# 指示書094：転職システム第1段階（既存4職間の転職基盤）

## ユーザーの依頼と決定

- 依頼（2026-11-09）：「次は転職の実装の調査をしてください。基本的には初代ウィザードリィの上位職を実装し、訓練所での転職機能の実装になると思います。ChatGPTがNotionの中に転職に関する試案をまとめたそうです。それを元にCodexへの指示書を作成してください。そのCodexの指示書をまずChatGPTにレビューさせて、その結果を私に報告してください。Codex実装はそのあとになります。」
- 全体仕様は Notion 試案「転職システム（8職業構成・提案仕様／未承認）」を現行コード（main eafdd4e）に合わせて具体化したもの。ChatGPT の指示書レビュー（要修正・条件付き承認、2026-11-09）の必須修正を反映済み。
- ユーザー決定1：転職回数に上限を設けない（試案の「最大2回」は採用しない）。履歴は記録するが回数制限・残回数表示はしない。
- ユーザー決定2：両系統の呪文を使えるメンバーの呪文選択ウィンドウに系統タブを付ける。
- ユーザー決定3：実装は2段階に分ける。本書は第1段階（既存4職間の転職基盤）。上級4職（侍・君主・忍者・司教）の追加は第2段階（095）で行い、本書の機構を再利用する。

## 第1段階の範囲

対象は既存4職（戦士・魔法使い・僧侶・盗賊）のあいだの転職とする。CLASSES への職業追加はしない。ただし、判定や習得の仕組みは「現在職」と「呪文の系統」を分離した形に作り、095 で職業と対応表を足すだけで上級職が載るようにする。

## 1. 転職の条件と判定

1. 町の訓練所でのみ実行可能（訓練所ダイアログからのみ操作できることで担保する）。
2. 対象はパーティーメンバーと控えの登録冒険者。状態が正常（status==='ok'）で、現在職の Lv が10以上。
3. 同一職への転職は不可。初期4職へはどの職業からでも転職できる（第1段階では前職条件はない）。
4. 回数上限なし。料金は無料。能力値の条件は設けない。
5. 転職先で装備できる武器が、そのメンバーの所持品に1本もない場合は転職を拒否し、理由を表示する。
6. 転職可否の判定は共通の純粋関数（例：canChangeClass(member, toJob)）に集約し、訓練所のボタン表示・候補一覧・確定直前の再判定で同じ関数を使う。判定関数にデータ変更の副作用を持たせない。候補表示と比較画面は実データを書き換えずに計算し、確定時に ID で対象を再検索して条件と所持武器を再検証する。転職処理は一度の確定で完結させ、失敗時に部分的な変更を残さない。

## 2. 転職時のデータ引継ぎ

| 項目 | 処理 |
| --- | --- |
| ID・名前 | 維持。所持金（s.gold）と図書館記録（s.library）は冒険全体の共有データであり、転職で削除・初期化しない。呪文の使用可否の正本は個人の known |
| job | 新しい番号（0〜3）へ更新。m.attack / m.ac は新職の CLASSES 値に合わせる |
| Lv / XP | Lv1 / XP0。前職の XP は持ち越さない |
| xpTargets | 新職の xpFactor で Lv2〜30 を再生成する（generateRecruit と同じ式）。xpCurveVersion は 2 のまま |
| HP上限 | 維持。以後は新職の hpGrowth で増える |
| MP上限 | max（転職前のMP上限, 新職の mp 基準値）。以後は新職の mpGrowth で増える |
| 現在 HP・MP | 上限まで回復する（パーティーは並行配列 s.hp/s.mp、控えはロスターレコード側を更新する） |
| STR / AGI | 現在値をそのまま引き継ぎ、その値を新しい baseStr / baseAgi（転職後の成長基準値）とする。成長上限18は変えず、転職を繰り返しても18を超えない |
| IQ / PIE | 維持。レベルアップでは成長しない（現行どおり） |
| 習得済み呪文 known | 転職した瞬間は一切変更しない。新規習得は転職後に新職でレベルアップしたときだけ行う（§4） |
| 所持品 | 維持（後述の装備付け替えを除き、削除・並べ替えをしない） |
| 現在の装備 | 装備スロットは所持品配列のインデックスを保持する（equipped、armor.head/body/feet、控えはレコード内）。付け替えは次の順序で厳密に行う：(1) 転職後も現在の武器を装備できる場合はそのスロットを維持する。(2) 装備できなくなる場合は、所持品配列の先頭から装備可能な「武器」だけを探して付け替える（防具・薬は候補に含めない）。(3) 防具は部位ごとに判定し、適合するものだけ保持し、合わない部位は未装備にする。(4) 確定後に AC と武器性能を再計算し、表示と戦闘計算を一致させる。(5) 装備可能な武器がない場合は何も変更せず転職を拒否する（§1-5） |
| 特殊能力 | 現在職のものだけが有効。前職の盗賊能力などは継承しない（判定はすべて現在職ベースの既存実装のままでよい） |
| 転職履歴 | careerHistory に {from（旧職番号）, fromLevel（転職時の Lv）, to（新職番号）} を追加する。回数は careerHistory.length から導出し、別の回数フィールドは持たない |

## 3. 呪文：使用側の分離（詠唱の職業一致を解消する）

現行コードでは「覚えている」と「唱えられる」が完全には分離されていない。次をすべて同じ権限ルール（known・状態異常・場面・MP・対象の有効性で判定し、現在職と呪文系統の一致は要求しない）に揃える。

- castMagic（dist/spells.js）の入口条件から `x.job!==jobOf(i)` を取り除く。
- calfoCaster() の術者選択から `magic('calfo').job===jobOf(i)` を取り除き、calfo を習得していて実際に使えるメンバーを選ぶ。
- renderMagic の一覧を現職系統だけでなく習得済み呪文すべてにする（タブは §5）。
- spellReason は現行どおり known ベースでよい。mahaman の「Lv1では使用不可」のような呪文固有の使用条件は転職後もそのまま残る。
- 敵の呪文抵抗など、系統を使う他の判定は変更しない。
- hasSpells（party.js、現行は job が [1,2] かで判定）を「習得済み呪文が1つ以上あるか」に変える。ステータス画面の呪文ボタン（renderStats の [1,2].includes 判定）も同じ考え方に揃える。これにより、呪文を1つも持たないメンバーには呪文コマンドが出ない（転職直後のメンバーも同様で、仕様として明記する）。

## 4. 呪文：習得側の分離（learnMagic の一般化）

- learnMagic を「対象系統」と「有効習得Lv」で決まる形に一般化する。第1段階の対応は次のとおり（095 で侍・君主・司教の行を足す）：魔法使い→魔法使い系・有効習得Lv＝職Lv、僧侶→僧侶系・有効習得Lv＝職Lv、戦士・盗賊→新規習得なし。
- レベルアップのたびに、有効習得Lv 以下の未習得呪文すべてを抽選対象にする（現行方式の維持）。抽選の成否は呪文の系統側の能力値を使う（魔法使い系は intelligence、僧侶系は piety、いずれも ÷30。現行は術者の職で選んでいるため、第1段階の4職では結果が同じになるが、系統側に直す）。
- ensureMagic は「旧データの欠損修復」の役割に限定し、転職や新職向けの自動付与は行わない。現行の特別付与（僧侶 Lv3 の watchful、Lv5 の floodfill、魔法使いの identifyfoe／dumapic／makanito）は現行職での付与結果を変えない。とりわけ identifyfoe と dumapic は現行ではレベル条件なしに魔法使いへ付与されているため、この挙動を変えないこと。現行4職での付与結果が変わらないことをテストで固定する。

## 5. 呪文ダイアログの系統タブ

- #magicdialog（renderMagic）で、両系統の習得呪文を持つメンバーには系統タブ（魔法使い／僧侶）を表示し、一覧をタブで切り替える。片系統しか持たないメンバーではタブを出さず、従来の見た目のままにする。
- 初期タブ：現職の系統を優先する（魔法使い→魔法使い系、僧侶→僧侶系。ただしその系統の習得呪文がある場合に限る）。現職に系統がない（戦士・盗賊）場合は習得済みの系統を開く（両方あれば魔法使い系を先にする）。
- タブを切り替えたら選択中の呪文（spellSelected）と対象候補をクリアする。ダイアログを開き直したら初期タブから始める。
- 戦闘中のコマンド入力と探索中の詠唱は同じダイアログを使うため、両方に効くこと。

## 6. 訓練所 UI とステータス表示

- 訓練所（dist/training.js、dist/index.html）：登録メンバー一覧の各行に「転職」ボタンを追加する。条件を満たさない場合はボタンを押せないようにし、理由が分かる表示にする。
- 転職ダイアログを新設する：職業一覧（4職）に特徴・可否を示し、職業を選ぶと転職前後の比較（Lv・XP・HP・MP・AC、使えなくなる装備、呪文が引き継がれること）と「Lv と XP がリセットされる」警告を表示する。確定は専用のボタンで行い、初期状態では転職先は未選択にする。Esc／キャンセルで閉じても状態は変わらない。キーボード操作（data-key-* の規約）とフォーカス管理は既存ダイアログに合わせる。
- ステータス画面：careerHistory があるメンバーには最新の前職を「前職：魔法使い Lv.10」のように表示する。
- 装備可否の判定は1つのヘルパーに集約する（第1段階では classes.includes(job) と等価でよい）。095 で上級職の互換表を差し込める形にし、転職時の付け替え判定と equip() が同じヘルパーを使うようにする。
- generateRecruit に「新規作成は job 0〜3 のみ」の検証を追加する（095 で CLASSES が増えたときの予防。現行の動作は変えない）。

## 7. セーブ互換

- セーブキー ash-v1 は維持。ロスター保存（rosterVersion:1）の構造は変えない。追加項目はメンバーオブジェクト内の任意項目として持つ。
- careerHistory の補完は ensureProfile で行い、パーティー・控えの両方を対象にする。欠損・不正値でも安全に空配列へ補完する。遺体（corpses 内のロスター記録）も職業番号と履歴を保持したまま往復できること。
- 読込後の不変条件：転職済みキャラクターの known・xpTargets・装備スロットは、セーブ読込や ensureProfile／render の繰り返し実行で変化しない。転職直後の状態と、保存→読込後の状態が一致すること。旧セーブ（職業0〜3のみ、careerHistory なし）はそのまま読み込め、自動で転職したり呪文を再抽選したりしない。

## 8. テスト要件（受け入れ条件）

新規テスト tests/class-change.cjs（tests/game.cjs に登録）と、訓練所ダイアログと呪文タブのブラウザテスト tests/class-change-browser.py を追加する。既存テストは全件合格を維持すること（期待値を緩めたり削除したりしない）。

1. 現行4職の新規登録・装備・戦闘・呪文・罠解除が従来どおり。
2. Lv10未満／状態が正常でないメンバーは転職できない。Lv10 の正常なメンバーは訓練所で候補と条件を確認できる。
3. 同職への転職は不可。回数上限がないこと（同じメンバーが3回以上転職できること）。
4. 転職で名前・ID・所持金・所持品・習得済み呪文・図書館記録が失われない。
5. 転職直後は Lv1／XP0 で xpTargets が新職係数で再生成される。その後のレベルアップで STR・AGI が転職時の値から巻き戻らない。
6. 元魔法使いの戦士が習得済み呪文を使える（戦闘コマンドに呪文が出て、castMagic まで通して実際に唱えられる）。MP も残るが、新しい魔法使い呪文は習得しない。転職後の calfoCaster が職業一致に依存せず術者を選ぶ。
7. 両系統の習得呪文を持つメンバーの呪文ダイアログにタブが出て、両系統を切り替えて唱えられる。片系統のみのメンバーにはタブが出ない。タブ切替で前のタブの選択呪文・対象が残らない。
8. 前職が盗賊でも、現在職が盗賊でなければ罠系能力は使えない。
9. 転職後に使えない装備は解除され、アイテムは消えない。武器・防具・薬が混在する所持品で、自動付け替えが正しい武器だけを選ぶ。現在の武器が転職後も使える場合は装備が維持される。
10. パーティー6人・控え・並べ替え・町帰還・全滅・遺体回収・保存／読込を通して転職データが保たれる。控えメンバーの転職→加入→保存→読込でデータが失われない。旧セーブのロードで誤変換が起きない。
11. 訓練所ダイアログのキーボード操作、確認キャンセルで状態が変わらないこと。確認画面を開いた後に条件が変わった状態で確定しても、不正な転職が成立しない。
12. 転職操作だけでは known が増えない。ensureProfile／render の繰り返し実行や、同じ保存データの複数回読込で、呪文・履歴・装備・XP が変わらない。
13. 転職を10回以上繰り返しても履歴・成長・能力値上限（18）が破綻しない。継承後も mahaman の使用条件、沈黙・MP不足・戦闘専用／探索専用の制約が正しく働く。
14. generateRecruit に job=4 を渡してもエラーにならず新規作成が拒否される。
15. 少なくとも1本、転職を確定→保存→読込→戦闘と探索で旧系統呪文を使う、通しのシナリオを含める。

検証は従来どおり：node tests/game.cjs 全件、ブラウザテスト全件（1280px／390px）、python3 scripts/compile-monsters.py --check、sim selftest、MANIFEST 照合、実経路での確認（実際の転職操作、実際の詠唱）。

## 9. 第1段階でやらないこと（095 の範囲）

- CLASSES への上級4職（侍・君主・忍者・司教）の追加と、その基礎値・成長係数・mpFromLevel。
- 上級職の前職条件、装備の読み替え互換（canEquipJob の互換表）、lootRecipient への互換適用。
- 侍・君主・忍者の攻撃回数と命中成長、君主の解呪、忍者の罠・宝箱率、starterWeapon の上級職対応、strengthFor／agilityFor の上級職基礎値。
- 司教の両系統習得・侍／君主の遅れ習得（有効習得Lv の追加行）。

# 指示書130: モンスター随伴機能（Partner）の導入（混合方式・設定例の先行）

日付: 2026-11-23
出典: Notion 実装予定DB 試案「モンスター随伴機能（Partner）導入試案」（2026-11-22作成、第12項に検証メモあり）
オーナー決定: 方式は**混合方式**（試案第12項の提案）。随伴表は**試案の設定例だけを先行**し、全種の表は後続指示で別途設計する。

## 1. 目的

通常遭遇と守護者戦の敵編成に、種ごとの随伴（Partner）設定による関連性を持たせる。列数の分布は現行（1〜3列・等確率、平均2列）を維持し、随伴設定のある種が先頭・途中の列に来たときだけ、設定された組み合わせが確率で現れるようにする。

## 2. 混合方式の定義（本指示の正本）

現行 `monsterFormation(boss)`（dist/monsters.js）の骨格は維持し、「次の列の種の決め方」だけを差し替える。

### 2.1 次列の決定規則（通常・守護者戦で共用）

直前の列の種 D について:

1. D に随伴設定があり（`partnerId` が非 null かつ `partnerRate > 0`）、随伴先が**現在の階で出現可能な非守護者**（随伴先の `floors` に現在階を含み、`boss` でない）なら、確率 `partnerRate` で抽選する。成功したら随伴先を次の列とする。
2. それ以外の場合（設定なし・随伴率0・随伴先が無効・抽選に失敗）は、現行どおり候補プールからランダムに1種を引く。

### 2.2 通常遭遇

1. 列数は現行どおり 1〜3 列を等確率で先に決める。
2. 先頭列は現行どおり候補プール（同階の非守護者＋撃破済みの同階守護者。指示書123の現行仕様）からランダムに引く。
3. 2列目以降は 2.1 の規則で、直前の列の種から順に決める。
4. 守護者の重複排除（最初の1列だけ残し、残りを非守護者へ置換する現行処理）は従来どおり最後に行う。随伴先は非守護者に限るため、随伴抽選が守護者を生むことはない。ランダム抽選で守護者が複数列に出た場合の置換も現行どおり。

### 2.3 守護者戦

1. 守護者に有効な随伴設定がある場合: 編成は [守護者, 随伴先] を確定とし（随伴率100%の設定を用いるため抽選は行わない）、3列目は現行どおり 50% の確率で存在し、その種は 2.1 の規則で随伴先の種から決める。
2. 守護者に随伴設定がない、または随伴先が無効な場合: 現行の編成（[守護者, ランダム, 50%でランダム]）をそのまま維持する（試案第7項の暫定措置）。
3. 撃破後の通常遭遇では、守護者にも同じ随伴設定が適用される（2.2 の規則どおり。試案第7項末尾）。

### 2.4 変えないもの

- 宝箱の抽選基準は戦闘開始時の先頭種の ID（現行どおり）。随伴種への変更や先頭死亡時の再抽選はしない。
- 各列の個体数（群れ）、経験値・金貨・状態異常・行動処理は現行どおり。同種が別列に出た場合は別グループとして扱い、呪文Lv・魔力低下（指示書127）も列ごとに独立のまま。
- 戦闘中の仲間呼び・増援は別機能で変更しない。
- セーブ形式（`ash-v1`）に変更はない。随伴はマスタデータのみで、戦闘状態への追加保存は不要。

## 3. データの追加

### 3.1 CSV とコンパイラ

- `data/monsters.csv` に列「随伴モンスターID」（固定ID文字列、未設定は空）と「随伴率」（0〜100の整数、未設定は0）を追加する。
- `scripts/compile-monsters.py` は各モンスターに `partnerId`（文字列または null）と `partnerRate`（0〜1の割合。`spell` と同じ流儀で率/100）を出力する。検証で次をエラーにする:
  - 随伴率が 0〜100 の整数でない。
  - 随伴率 > 0 なのに随伴モンスターIDが空、または実在しないID。
  - 随伴先が守護者（boss）である。
  - 随伴先と出現階層が1つも重ならない（どの階でも成立しない死んだ設定）。
- `python3 scripts/compile-monsters.py` で `dist/monster-data.js` を再生成し、`--check` が通ること。

## 4. 実装

- `dist/monsters.js` の `monsterFormation` を第2項の定義で書き換える。次列決定の共用ヘルパを置き、通常・守護者戦の両方から使うこと。
- 随伴先の有効判定は実行時に行う（現在階の `floors` に含まれる非守護者）。コンパイル時検証（3.1）はデータの誤りを早期に止めるためのもので、実行時判定を省略してよい理由にはならない。
- SPECIFICATION.md の通常遭遇の編成の記述（1〜3列を抽選する旨の段落）を、混合方式の随伴に触れる現行の内容へ更新する。

## 5. テスト

新規テスト `tests/partner-formation.cjs` を追加し、`tests/game.cjs` の require リストへ登録する。乱数を固定（`Math.random` の差し替え）して次を検証する:

- 随伴率100%相当の設定では随伴先が必ず次の列になる（データ上の最大は守護者の100%。通常種は率を差し替えたフィクスチャか、抽選境界の固定で検証する）。
- 随伴設定のない種・随伴率0では随伴抽選が起きず、従来のランダム編成と列数分布（1〜3列）が変わらない。
- 随伴先が現在階で出現できない種、または守護者の場合は随伴抽選を行わずランダムになる。
- 連鎖の例: 高位の魔術師 → トロル（50%）→ 忍びの者（トロルの30%）が、固定乱数で再現できる。
- 列数は常に最大3列。同種随伴（ゴブリン→ゴブリン）で複数列が同種になっても別列として返る。
- 守護者戦: 設定のある守護者（屍術師・吸血鬼・迷宮の主）は最低2列で、2列目が専用随伴先になる。設定のない守護者は現行編成の範囲（2〜3列、先頭が守護者）にある。
- 撃破済み守護者の通常遭遇で、守護者が複数列に現れない（指示書123の重複排除が随伴導入後も効く）。
- 宝箱の基準が先頭種のままであること（既存テストの回帰確認で足りる場合はその旨を報告に記す）。

既存テストが編成の現行挙動を固定している場合は、新仕様への追従として期待値を更新してよいが、検証の強さを落とさないこと。守護者の重複排除や宝箱基準など、変えていない仕様のテストはそのまま通ること。

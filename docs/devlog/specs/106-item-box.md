# 指示書106: アイテムボックスの導入

## ユーザーの依頼（原文）

「実装の依頼です。アイテムボックスを導入しようと思います。町にいる時のみ、パーティーステータス画面から各人のアイテムウィンドウ、また鍛冶屋の「アイテム・売却」からのアイテムウィンドウでそれぞれ同じアイテムボックスを開けるようにします。
アイテムボックスの容量は全部で100で、図鑑と同様に武器・頭・胴体・足・アイテムのタブで分かれています。
アイテムボックスウィンドウではアイテムボックスからアイテムを取り出せたり、アイテムを預けたりできます。」

（解釈は Muse が提示し、ユーザーが承認した：アイテムウィンドウ内のボタンから開く、対象メンバーはアイテムウィンドウを開いている本人、装備中は預け不可、セーブに保存する。実装は Codex で行う。）

## 現行挙動（確認済み）

- アイテムウィンドウは #inventorydialog で、ステータス画面の各人の「アイテム」ボタンと、鍛冶屋の「アイテム・売却」ボタンの両方が openInventory(i) 経由で同じダイアログを開く。対象メンバーは inventoryMember に保持される。タイトルに所持数 n/10 が出る。
- 所持品は s.inventory[i]（アイテムIDの配列、上限10）。装備中判定は isEquipped(i, slot)。売却 sell(i, slot) は町限定・装備中不可で、splice 後に装備・防具のスロット参照を詰め直す（この詰め直しが既存パターン）。
- アイテムの分類は図鑑（dist/library.js）と同じ式：`w.kind==='medicine' ? 'medicine' : (w.part || 'weapon')`（weapon/head/body/feet/medicine）。
- セーブは rosterSaveState() が {...s} を土台にするため、s のトップレベルに置いた配列はそのまま保存・書き出し対象になる。読み込み検証 validateSaveData() は任意フィールドを「あれば検証する」形式（`'key' in data` のパターン）。

## 実装内容

### 状態

- `s.itemBox`：アイテムID（文字列）の配列。パーティ共通で1つ。容量は全カテゴリ合計で最大100。
- 新規開始・リセット時は空。itemBox を持たない古いセーブを読み込んだ場合は空のボックスとして扱い（読み込みで落ちないこと）、次回保存から保持される。

### 入口

- #inventorydialog 内に「アイテムボックス」ボタンを追加する。表示は町にいる時だけ（売却ボタンと同じく s.area==='town' の条件で描画する。迷宮内のアイテムウィンドウには出さない）。
- ボタンを押すと、対象メンバー（inventoryMember）のままアイテムボックスのダイアログを開く。ステータス画面経由でも鍛冶屋経由でも同じボックス（同じ s.itemBox）を見せる。
- ボックスを閉じるとアイテムウィンドウに戻る（ダイアログの重ね表示は訓練所と酒場の既存パターンに倣う）。

### アイテムボックスのダイアログ（新規）

- タイトル「アイテムボックス」、容量表示（ボックス n/100 と対象メンバーの所持 n/10）、通知欄（role=status）。
- タブは図鑑と同じ体裁（.library-tabs、role=tablist）で5つ：武器・頭・胴体・足・アイテム。分類は上記の式を使う。
- 各タブに2つのグループを表示する：
  - 「ボックス」：そのカテゴリのボックス内アイテムを1点ずつ行にし、名前と「取り出す」ボタン。
  - 「（メンバー名）の所持品」：そのカテゴリの所持品を1点ずつ行にし、名前と「預ける」ボタン。装備中のアイテムは行は出すが「預ける」を無効にし、装備中と分かる表示にする。
- 預ける（deposit）：
  - 条件：町・idle・対象スロットにアイテムがある・装備中でない・ボックスが100未満。満たさない場合は何も変えず、理由を通知欄に出す（ボックス満杯時）。
  - 処理：sell() と同じ詰め直し（splice したスロットより後ろの装備・防具参照を1つ詰める）で所持品から外し、IDを s.itemBox へ追加する。
- 取り出す（withdraw）：
  - 条件：町・idle・ボックスにそのアイテムがある・対象メンバーの所持品が10未満。満たさない場合は何も変えず、理由を通知欄に出す（所持品満杯時）。
  - 処理：s.itemBox から外し、対象メンバーの所持品の末尾へ追加する。
- 操作のたびにボックス側と背後のアイテムウィンドウ側の両方を再描画し、保存されること（render() の保存経路に乗ること）。
- キー操作は他のダイアログの慣例（data-key-back 等、keynav.js の仕組み）に合わせる。

### セーブ・読み込み

- validateSaveData() に任意フィールドの検証を追加する：`'itemBox' in data` の場合、文字列の配列で長さ100以下でなければ不正とする（既存の任意フィールドと同じ書き方）。
- JSON の書き出し・読み込みでもボックスが保持される（rosterSaveState の土台に乗るため、追加の移送処理は不要なはずだが、テストで往復を確認すること）。

### 仕様書

- docs/SPECIFICATION.md の「4. 装備・アイテム」に、アイテムボックス（入口・容量100・タブ・預ける／取り出すの条件・装備中不可・セーブに保存される）を追記する。

## テスト

- 新規 tests/item-box.cjs（tests/game.cjs に登録）：
  - 預ける：通常の預け入れ、装備中の拒否、装備より前のスロットを預けたときの装備・防具参照の詰め直し、ボックス100での拒否
  - 取り出す：通常の取り出し、所持10での拒否
  - 分類：武器・頭・胴体・足・薬が各カテゴリに振り分けられる
  - 保存往復：rosterSaveState → restoreRoster でボックスが保持される、itemBox のない旧セーブ相当のデータが空ボックスとして読み込める
  - 読み込み検証：itemBox が文字列配列・100以下なら受理、それ以外（101超・非文字列）は拒否される
- 新規 tests/item-box-browser.py：
  - ステータス画面経由と鍛冶屋「アイテム・売却」経由の両方で同じボックスが開く、タブ切り替え、預ける→取り出すの往復、迷宮内ではボタンが出ない、1280px／390px、JSエラーなし

## 制約

- dist のファイル数は増やさない（既存ファイルへの追加で実装する）。セーブキー ash-v1 を維持し、新フィールドは任意（欠けていても読める）にする。
- 戦闘・探索中のアイテム使用、購入、売却、譲渡の既存挙動は変えない。
- 敵データには触らない。
- 検証：node tests/game.cjs 全件、関係するブラウザテスト、python3 scripts/compile-monsters.py --check、sim selftest、MANIFEST 一致。

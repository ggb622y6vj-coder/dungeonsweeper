# 130 モンスター随伴機能の導入

実施日 2026-11-23

## 着手前照合

指示書130の全文を読み、`monsterFormation`、敵CSV、コンパイラ、生成データ、Notionスナップショットと同期テストを照合した。108種のうち指定12組はすべて固定ID・名称が一致し、随伴先は共通の出現階を持つ非守護者だった。5Fでは高位の魔術師・トロル・忍びの者の3種が同じ階に出現する。

現行コードは通常戦の列数を先に1〜3列から等確率で選び、撃破済みの同階守護者を候補に加え、最後に守護者の重複を除く。守護者戦は最低2列で、3列目の出現率は50%。この骨格で混合方式を実装でき、仕様判断を保留する不整合はなかった。変更前の `node tests/game.cjs` は242件合格。

## 実装内容

- `data/monsters.csv` と `data/notion-monsters.json` の全行に随伴モンスターIDと随伴率を追加した。通常種9種と守護者3種を設定し、残り96種は空文字・0とした。
- コンパイラは随伴率の整数範囲、正の率に対するIDの有無、指定IDの実在、非守護者であること、出現階の重なりを検証する。0%で実在する有効なIDを指定した場合は無効な抽選設定として保持する。`dist/monster-data.js` はコンパイラで再生成した。
- 通常戦の2列目以降と専用随伴がいる守護者戦の3列目に共通の次列選択処理を使う。随伴先は毎回、現在階の非守護者候補からIDで特定する。設定が無効なら随伴抽選の乱数を消費せず、各戦闘の候補から引く。
- 専用随伴を持つ守護者戦では2列目を抽選なしで確定する。専用随伴がない場合は、2列目が随伴設定を持つ種でも3列目を独立に引く。撃破後の通常戦で守護者を引いた場合は通常の次列選択を適用する。`docs/SPECIFICATION.md` 第5節に両方の扱いを記載した。

## 回帰テストと既存テストの変更

- 新規 `tests/partner-formation.cjs` は12種の設定値と残り96種の未設定、列数の両境界、随伴抽選の成功・失敗、5Fの連鎖、同種の別列、現在階にいない種・守護者・存在しないIDからのフォールバックを固定乱数で検証する。専用随伴3種については、守護者戦の2列・3列と、通常戦で随伴を挟んで再度引いた守護者だけが置換されることを確認する。
- `tests/game.cjs` は新規テストを登録した。`tests/notion-sync.cjs` は108行の新列の型と随伴率の範囲を確認し、空文字をnull、百分率を割合に変換してゲームデータと照合する。
- `tests/encounter-adjustments.cjs` は新仕様への追従として、指示書123の連続守護者抽選と専用随伴なしの守護者戦を検証する間だけ、各階の先頭候補と守護者の随伴率を0にした。100%随伴があると守護者を連続して引けないため。元の固定乱数・期待配列・乱数消費数の検証を維持し、各階の検証後に率を戻す。実データでの重複排除は新規テストでも確認した。
- 宝箱基準は既存の `tests/chest-loot.cjs` で確認した。先頭種IDが保存・再読込後も残り、先頭列が逃走し、増援を含む敵の順番が変わっても同じ宝物グループを使う。
